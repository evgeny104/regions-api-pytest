# Чек-лист требований и проверок Regions API

## Входы и результаты

- Вход: контракт `tz-extracted.txt`, текущий чек-лист и тесты в `tests/func/`
  и `agents-test/func/`.
- Результат: обновлённый `agents-test/checklist/api-checklist.md` с
  трассируемыми требованиями и фактическим покрытием.
- Если `agents-test/checklist/` ещё не существует, создай её.
- Редактируй только `agents-test/checklist/api-checklist.md`; остальные файлы
  проекта доступны только для чтения. `tests/func/` — пример стиля и исходного
  покрытия, не запускай и не изменяй его.
- Для тестовой архитектуры используй `.agents/skills/regions-api-test-authoring/SKILL.md`.

## Порядок работы

1. Разбери `tz-extracted.txt`; для каждого требования сохрани страницу и ближайший заголовок, таблицу или фрагмент.
2. Разложи контракт на атомарные проверяемые требования со стабильными ID
   `API-001`, `API-002` и далее.
3. Для каждого ID опиши область/endpoint, вход или предусловия и проверяемое ожидаемое поведение. Не указывай статус или
   поля ответа, если текст контракта их не задаёт.
4. Разработай набор сценариев с помощью подходящих техник тест-дизайна:
   классы эквивалентности; анализ граничных значений; позитивные и негативные
   проверки; таблицы решений/комбинации параметров; проверки структуры и
   семантики полей; переходы и последовательности запросов для пагинации.
   Применяй технику только в пределах явно заданного контракта. Если граница,
   допустимое значение, порядок, ошибка или сочетание не определены, запиши
   неопределённость вместо придумывания ожидаемого результата.
5. Разложи применимые классы/границы на отдельные атомарные строки с уникальными
   ID. Для каждой укажи предусловия, входные данные, конкретное проверяемое
   поведение и ожидаемое наблюдение, чтобы тестировщик мог связать ID с assert.
6. Сверь пункты отдельно с `tests/func/` и `agents-test/func/`. Считай пункт
   покрытым лишь после чтения теста и подтверждения, что его assert проверяет
   соответствующее поведение. Для покрытых пунктов называй точный путь к тесту.
7. Неизученные тесты не считай покрытием. Для частичного покрытия укажи конкретно, что проверяется и чего не хватает.
8. Сохраняй существующие ID при обновлении; не перенумеровывай пункты без необходимости. Удали дубли только после сверки
   ссылок на ID.
9. Необоснованные тестовые сценарии и идеи не включай в таблицу требований; помещай их в вопросы, если они указывают на
   пробел контракта.
10. Веди измеримый тест-план: для каждого атомарного сценария укажи test-case ID, применённую технику тест-дизайна,
    обязательные входы/предусловия, ожидаемое наблюдение и точку проверки. Разделяй обязательное контрактное покрытие и
    сравнительные пользовательские сценарии из `tests/func/`; пользовательские тесты не превращают неподтверждённое
    ожидание в требование API.
11. Сводка покрытия должна отдельно считать атомарные сценарии всего, применимые, полностью покрытые, частично покрытые,
    непокрытые и исключённые с причиной; число pytest-кейсов и assertions приводи как справочные метрики, не как
    доказательство полноты. Любой пункт «Частично» должен перечислять недостающие assertions; непокрытый пункт нельзя
    скрывать в агрегате.
12. Каждому контрактному сценарию присвой стабильный `TC-...` ID и привяжи его к `API-...`. Статус ставь по assertions в
    коде, а фактический результат последнего запуска указывай отдельно: падение теста означает execution `FAIL`, но не
    отсутствие покрытия.

## Формат `agents-test/checklist/api-checklist.md`

Каждый блок сценария и требования должен содержать:

- ID и endpoint/область.
- Требование, сценарий и ожидаемый результат.
- Источник в `tz-extracted.txt`.
- Статус покрытия и точный тест/assertion.

Статус покрытия: `Не покрыто`, `Покрыто`, `Частично`, `Не применимо`. Для `Покрыто` и `Частично` укажи test-case ID, путь
к тесту и точный смысл assert. В конце веди разделы «План тестирования и метрики покрытия», «Непокрытые требования» и
«Вопросы и неопределённости». План должен раздельно показывать сценарии и assertions для агентской и пользовательской
suite; дату и результат прогона добавляй только по подтверждённому логу.

## Ограничения

- Не используй PDF как источник требований; работай по `tz-extracted.txt`.
- Не приписывай контракту правила, отсутствующие в тексте.
- Не считай наличие теста достаточным без проверки его assert.
- Не запускай тесты и не редактируй production-код или тесты.
- Не трактуй падение теста как доказательство дефекта API.
- Перечисляй недоступные источники и непроверенные пункты.
