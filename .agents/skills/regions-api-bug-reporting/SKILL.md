# Отчёты о результатах агентского прогона

## Цель и критерии подтверждения

Один отчёт описывает одну подтверждённую первопричину дефекта API или одно
отдельное неподтверждённое наблюдение/ожидание теста. Все pytest-кейсы,
затронутые этой причиной, перечисляются вместе в одном отчёте с результатом
каждого. До создания записи установи связь между:

1. конкретным требованием контракта в `tz-extracted.txt`;
2. наблюдаемым поведением API;
3. ожидаемым и фактическим результатом;
4. доказательством наблюдения.

Падение теста само по себе не доказывает дефект сервиса. Ошибка тестового кода,
неверная конфигурация, недоступность окружения и неоднозначное требование
должны быть исключены либо явно обозначены как неразрешённые альтернативы.

Если доказательств недостаточно, создай только запись о наблюдении и явно
укажи, почему нарушение контракта не подтверждено.

## Перед созданием

1. Прочитай `tz-extracted.txt`, правила функциональных тестов в
   `.agents/skills/regions-api-test-authoring/SKILL.md`, связанный чек-лист
   `agents-test/checklist/api-checklist.md`, тесты из `agents-test/func/` и
   предоставленный лог агентской suite. Не используй `tests/func/` или
   пользовательские баг-репорты как источник фактов для отчёта.
2. Проверь, что наблюдаемое поведение нарушает конкретное требование контракта.
3. Разделяй подтверждённые факты, неизвестные данные и гипотезы.
4. Для текущего запуска обработай все результаты из тестового лога
   `agents-test/func/`. Создавай один отчёт на одну установленную причину,
   включая неподтверждённое наблюдение, если причина пока не установлена.
   Объединяй падения разных pytest-кейсов, только когда доказательства
   подтверждают общую причину; не объединяй независимые причины. В каждом
   отчёте перечисли все затронутые pytest node ID и индивидуальный результат
   (например, failed, passed, skipped или xfailed), а для падений — ожидаемое
   и фактическое поведение. Классифицируй явно: нарушение контракта,
   неподтверждённое/ошибочное ожидание теста, неопределённость контракта или
   инфраструктурная ошибка. Не называй неподтверждённые ожидания дефектами API.
5. Создавай отчёты только по доказательствам текущего агентского цикла. Не
   используй исторические отчёты в общем архиве или пользовательские тесты как
   доказательство нового дефекта. Архив можно просматривать только для выбора
   уникального ID и предотвращения дубликатов.
6. Для нового наблюдения используй следующий свободный BUG-ID среди отчётов в
   `agents-test/bug/`. Не создавай дубликат того же падения текущего запуска.
7. Не придумывай ответы API, окружение, частоту воспроизведения, влияние или причину.

## Формат файла

Создавай отчёты и дополнения на русском языке только в
`agents-test/bug/YYYY-MM-DD/`, где дата —
дата прогона, выявившего дефект. Имя файла:
`BUG-NNN-short-kebab-title.md`.
Создавай каталог даты и родительские `agents-test/bug/`, если они отсутствуют.
Ограничивай строки 121 символом, перенося длинный текст на следующую строку.

Если пользователь не попросил другой язык, используй разделы:

1. Заголовок с кратким симптомом.
2. Метаданные: Severity, Priority, Component, Env, Reporter, Date.
3. Описание дефекта и его наблюдаемое влияние.
4. Нарушенное требование: `tz-extracted.txt`, страница или раздел, ожидаемое правило.
5. Условия и точные шаги воспроизведения; метод, endpoint и параметры.
6. Expected и Actual: конкретные статусы, поля или значения ответа.
7. Evidence: минимальный безопасный фрагмент ответа, лог или ссылка на прогон.
8. Связанный регрессионный тест: путь и имя теста, если он существует.

## Достоверность, безопасность и классификация

- Указывай Severity и Priority только если они обоснованы доступными фактами.
  Иначе явно напиши, что оценка не определена.
- Предполагаемую причину добавляй только отдельным блоком и явно помечай
  как гипотезу; не выдавай её за установленный факт.
- Не включай реальные секреты или чувствительные данные; используй `{BASE_URL}`
  вместо значения из `src/config/url.py`.
- Не публикуй полные токены, персональные данные или ненужные фрагменты ответов.
- Не утверждай, что дефект воспроизводится стабильно, если частота не проверялась.

## Редактирование и качество

- Перед созданием проверь номера и дубликаты в общем архиве `agents-test/bug/`;
  содержимое старых отчётов не используй как доказательство нового дефекта.
- Не создавай, не изменяй и не удаляй файлы вне `agents-test/bug/`.
- Создавай один отчёт на одну причину, а не на каждый отдельный pytest-кейс.
  Внутри отчёта перечисли все затронутые pytest node ID и результаты каждого;
  для каждого падения укажи ожидаемый и фактический результат, источник
  доказательства и классификацию подтверждённости.
- Не запускай тесты. Для фактического результата используй приложенный отчёт
  прогона автора; авторский прогон должен быть ограничен `agents-test/func/`.
- Каждая инструкция воспроизведения должна быть выполнимой без догадок.
- Сверь Expected с `tz-extracted.txt`, Actual с имеющимся наблюдением, а ссылку
  на тест — с существующим тестом.
- Соблюдай ограничения на сетевые тесты из skill автора.
- Не создавай фиктивные ссылки на тесты и прогоны.
- Проверь обязательные разделы, секреты, уникальность номера, соответствие
  одного отчёта одной причине и полноту списка затронутых кейсов и результатов.

## Итоговое сообщение

Укажи путь к созданному или обновлённому отчёту, требование контракта и связанный
регрессионный тест, если он есть. Отдельно перечисли отсутствующие доказательства
и поля, которые невозможно было подтвердить.
