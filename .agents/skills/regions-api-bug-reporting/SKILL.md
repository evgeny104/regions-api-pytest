# Репорты о дефектах Regions API

## Перед созданием

1. Прочитай `tz.pdf`, правила функциональных тестов в skill автора, связанные
   API-тесты и существующие файлы в `bug/`.
2. Убедись, что описано наблюдаемое поведение, которое нарушает конкретное
   требование контракта. Падение теста само по себе не доказывает дефект сервиса.
3. Разделяй подтверждённые факты, неизвестные данные и гипотезы. Не придумывай
   ответы API, окружение, частоту воспроизведения, влияние или причину.
4. Проверь номера существующих отчётов и используй следующий свободный
   `BUG-NNN`; не переиспользуй номер. Один отчёт описывает один дефект.

## Формат файла

Создавай отчёт на русском языке в папке `bug/YYYY-MM-DD/`, где дата — дата
прогона, выявившего дефект. Имя файла: `BUG-NNN-short-kebab-title.md`.
Ограничивай строки 121 символом, перенося длинный текст на следующую строку.
Если пользователь не попросил другой язык, используй разделы:

1. Заголовок с кратким симптомом.
2. Метаданные: Severity, Priority, Component, Env, Reporter, Date.
3. Описание дефекта и его наблюдаемое влияние.
4. Нарушенное требование: файл `tz.pdf`, страница или раздел, ожидаемое правило.
5. Условия и точные шаги воспроизведения; укажи метод, endpoint и параметры.
6. Expected и Actual: конкретные статусы, поля или значения ответа.
7. Evidence: минимальный безопасный фрагмент ответа, лог или ссылка на прогон.
8. Связанный регрессионный тест: путь и имя теста, если он существует.

Не включай реальные секреты или чувствительные данные; используй `{BASE_URL}`
вместо значения из gitignored `src/config/url.py`. Severity и Priority указывай
только если их можно обосновать доступными фактами; иначе явно напиши, что
оценка не определена. Предполагаемую причину добавляй только отдельным блоком
и явно помечай как гипотезу; не выдавай её за установленный факт.

## Редактирование и качество

- Если отчёт об этом же дефекте уже есть, обнови его вместо создания дубликата.
- Проверяй номер по всем папкам дат внутри `bug/`; не переиспользуй `BUG-NNN`.
- Пиши коротко и проверяемо; убирай повторы, расплывчатые слова и неподтверждённые
  обещания о влиянии.
- Каждая инструкция воспроизведения должна быть выполнимой без догадок.
- Сверь Expected с `tz.pdf`, Actual с имеющимся наблюдением, а ссылку на тест —
  с существующим тестом. Соблюдай ограничения на сетевые тесты из skill автора.
- В итоговом сообщении укажи путь к отчёту, требование контракта и связанный
  тест, если он есть; отдельно обозначь отсутствующие доказательства.
