# Создание функциональных тестов Regions API

## Цель и границы

Создавай и изменяй агентские функциональные API-тесты в `agents-test/func/`.
Если каталога нет, создай его перед записью тестов.
Существующие тесты в `tests/func/` служат только read-only образцом стиля;
не изменяй и не запускай их без отдельного поручения. Создавай все тестовые
артефакты только в `agents-test/func/`.
Не изменяй production-код в рамках роли автора тестов. Не меняй смысл
требований контракта ради прохождения тестов или CI.

## Источники истины

- Чек-лист требований API: `agents-test/checklist/api-checklist.md`.
- Извлечённый контракт API: `tz-extracted.txt`.
- Общие функциональные фикстуры: корневой `conftest.py`.
- Маркеры pytest: `pyproject.toml`.
- Образцы стиля и исходное покрытие: связанные тесты в `tests/func/`.
- Агентские тесты и покрытие: связанные тесты в `agents-test/func/`.
- Правила оформления подтверждённых дефектов:
  `.agents/skills/regions-api-bug-reporting/SKILL.md`.

## Стиль и архитектура текущего проекта

Существующие файлы `tests/func/test_*.py` — обязательный образец стиля.
Перед добавлением теста прочитай ближайшие по параметру и сценарию тесты, а
также корневой `conftest.py`, `src/api/region_client.py`,
`models/Pydantic/region.py` и `pyproject.toml`. Сохраняй текущую структуру,
имена, язык описаний и соглашения проекта; не вводи параллельную архитектуру.

- Размещай функциональные сценарии в подходящем `agents-test/func/test_*.py` по
  query-параметру или комбинации параметров. Используй тестовые классы
  `TestRegions...` и методы `test_...`, как в соседних файлах.
- Для обычных запросов используй существующий клиент `Region` только через
  фабрику `regions_request` и обёртки `region_response`/
  `region_response_pair`. Не создавай прямые вызовы `requests` в тестах и не
  обходи `src/config/url.py` с `BASE_URL`.
- Один запрос параметризуй через indirect `region_response`; пару запросов для
  сравнения — через `region_response_pair`, сохраняя одинаковые параметры,
  кроме меняемого номера страницы. Для последовательных зависимых запросов
  используй `regions_request` с метками `label`, как в `test_pagination.py`.
- Помни, что корневой `conftest.py` выбирает `RegionResponse` или
  `RegionErrorResponse`, валидирует тело Pydantic и возвращает тесту пару
  `(status_code, validated.model_dump())`. В assertions используй этот
  валидированный словарь (`data["items"]`, `data["error"]`); не добавляй
  повторную Pydantic-валидацию в тестах и не ослабляй модели ради ответа.
  Каждый API-ответ агентских тестов обязан проходить эту Pydantic-валидацию.
  Не используй сырые ответы или ручную проверку схемы вместо Pydantic. Если
  контрактное поле отсутствует в модели, сообщи о нужном изменении схемы; не
  обходи валидацию.
- Для наборов входов используй `pytest.mark.parametrize` и
  `pytest.param(..., id="...")` с коротким, понятным сценарием. Передавай
  фикстуры косвенно (`indirect=True` или `indirect=[...]`) в стиле соседних
  тестов. Объединяй однотипные проверки параметризацией, когда это делает
  сценарии яснее.
- Описывай группу тестов русским docstring класса. Первая строка используется
  autouse-фикстурой `_allure_class_grouping` для группировки в Allure. Добавляй
  краткий docstring методу, когда он поясняет сценарий или связанный ID.
  Фикстура уже добавляет URL, параметры и тело ответа в Allure; не дублируй
  `allure.attach` и ручные suite/feature labels без конкретной необходимости.
- Используй только зарегистрированные в `pyproject.toml` маркеры:
  `smoke`, `negative`, `boundary`, `combined`, `pagination`. Назначай их по
  смыслу сценария. Не добавляй маркер без регистрации в конфиге.
- `pytest.mark.xfail` добавляй только для подтверждённого дефекта, с точной
  ссылкой `BUG-NNN` и `strict=True`. Не копируй существующий `xfail` или
  предположение из старых тестов без проверки актуального отчёта и основания.
- Проверяй статус, отсутствие/наличие `error` и значимые поля через явные
  assertions с понятным сообщением, следуя стилю соседних тестов. Не считай
  тестовые ожидания источником контракта: стиль можно наследовать, ожидания —
  только из ID чек-листа и `tz-extracted.txt`.

Примеры выбора паттерна из `tests/func/`: `test_country_code.py` для одного
параметризованного фильтра, `test_combined.py` для комбинаций параметров,
`test_pagination.py` для сравнения страниц и последовательных запросов,
корневой `conftest.py` для валидации ответа и интеграции Allure. Эти примеры
задают форму теста, но не подтверждают все содержащиеся в старых тестах
ожидания контракта.

Если обязательный источник недоступен или требование неоднозначно, не придумывай
ожидаемое поведение. Укажи, чего не хватает, и запроси уточнение, если без него
нельзя безопасно продолжить.

## Паритет с пользовательской suite

Когда пользователь просит довести агентское покрытие до уровня `tests/func/`,
используй раздел parity в `agents-test/checklist/api-checklist.md` как явный
список сценариев для сравнения. Реализуй контрактно обоснованные сценарии как
обязательные проверки. Дополнительные пользовательские границы, ошибки и
defaults, которые контракт не определяет, добавляй только как отдельные
characterization проверки с явным комментарием/ID и без статуса контрактного
требования. Не переноси пользовательские тесты или ожидания в баг-репорты:
баги полного цикла определяются только по агентской suite. Не меняй
`tests/func/`.

## Предусловия запуска

- Пользователь явно разрешил запускать тесты и проводить mutation-check для
  агентских изменений в `agents-test/func/`.
- Функциональные тесты вызывают API. Запускай их только при явной просьбе,
  подготовленном окружении и настроенном `src/config/url.py` с `BASE_URL`.
- Используй `.venv` и `pytest` так, как описано в `README.md`; не устанавливай
  зависимости глобальным `pip`.
- Запускай только агентские тесты командой
  `.venv\Scripts\python.exe -m pytest agents-test/func/`. Исходная suite
  `tests/func/` нужна только как read-only образец и не включается в прогон.
- Если предусловия не выполнены, не запускай сетевые тесты. Сообщи причину.
- Просмотр кода, diff и статический анализ не равнозначны запуску тестов.

## Обязательная проверка чувствительности assertion

После написания теста и успешного обычного прогона выполни mutation-check
каждого нового ключевого assertion:

1. Сохрани исходный файл и внеси минимальную временную мутацию в проверяемый
   тест (например, измени ожидаемое значение или условие assertion так, чтобы
   исправный ответ ему не соответствовал).
2. Запусти только этот тест через `.venv` и убедись, что он падает именно на
   мутированном assertion. Падение на сборе, фикстуре, сети, конфигурации или
   другом assertion не подтверждает чувствительность.
3. Немедленно восстанови оригинальный assertion, проверь diff, затем повторно
   запусти исходный тест. Убедись, что временная мутация не осталась.
4. Не оставляй `xfail`, ослабленное условие или временные файлы после проверки.
   Не изменяй API-клиент или production-код для мутации.
5. В отчёте укажи для каждого теста обычный результат, мутацию, точное место
   падения и результат повторного прогона. Если `.venv`, `BASE_URL` или API
   недоступны, не заявляй mutation-check успешным и укажи конкретную причину.

Mutation-check проверяет, что тест обнаруживает искусственно внесённое
несоответствие assertion. Он не заменяет проверку API-контракта на стенде.

## Порядок работы

1. Найди релевантный пункт в `agents-test/checklist/api-checklist.md` и сверь
   его источник и ожидаемое поведение с `tz-extracted.txt`; прочитай соседние
   тесты.
2. Сопоставь сценарий с существующим покрытием; выбери подходящий тестовый файл
   по query-параметру или комбинации параметров.
3. Используй pytest, существующие фикстуры, Pydantic-схемы, зарегистрированные
   маркеры и Allure. Не добавляй зависимости или новый тестовый фреймворк.
4. Для одного запроса используй indirect-фикстуру `region_response`.
   Для сравнения двух страниц используй `region_response_pair`; сохраняй
   одинаковые параметры, кроме номера страницы, если сценарий не проверяет иное.
   Для последовательных запросов с зависимыми параметрами используй
   `regions_request` напрямую.
5. Параметризуй наборы входных данных через `pytest.mark.parametrize` и
   `pytest.param`; используй читаемые `id` и добавляй сценарий в класс с docstring.
   Первая строка docstring используется для группировки теста в Allure.
6. Проверяй статус, валидированное тело ответа и значимые поля по контракту.
   В негативных сценариях проверяй конкретные поля ошибки, когда контракт их задаёт.
7. Используй только зарегистрированные маркеры. Новый маркер сначала добавь
   в `pyproject.toml` и сообщи об этом пользователю.
8. Для `total` следуй явному контракту. Если неясно, считается ли оно до или
   после фильтрации, сравнивай ответы только как characterization и не
   представляй это сравнение как обязательное контрактное ожидание. Не
   вычисляй последнюю страницу по `total` при активном фильтре, пока семантика
   фильтра явно не подтверждена.
9. Не ослабляй ассерты, чтобы сделать CI зелёным. Подтверждённый дефект можно
   пометить `pytest.mark.xfail(reason="BUG-XXX: …", strict=True)` только при
   наличии обоснования и ссылки на соответствующий дефект.
10. При подтверждённом нарушении контракта или запросе на оформление дефекта
    следуй `.agents/skills/regions-api-bug-reporting/SKILL.md`. Не создавай
    репорт на основании одной лишь ошибки тестового кода или гипотезы.
11. Изучи итоговый diff и проверь, что изменения ограничены поставленной задачей.

## Интеграция Allure

Функциональные фикстуры уже добавляют в Allure URL, query-параметры и тело
ответа; autouse-фикстура группирует тесты по docstring класса. Используй эти
фикстуры и docstring, чтобы новый тест попал в существующие группы и получил
данные запроса. Не добавляй повторные `allure.attach` или ручные метки без
необходимости. Результаты создаются при запуске pytest с `--alluredir=allure-results`.

## Критерии завершения

Перед завершением убедись, что:

- сценарий связан с ID пункта чек-листа и конкретным требованием контракта;
- выбранная фикстура соответствует сценарию;
- проверки способны обнаружить регрессию и не противоречат контракту;
- использованы существующие модели, маркеры и стиль проекта;
- diff в `agents-test/func/` просмотрен и не содержит посторонних изменений;
- в итоговом сообщении перечислены изменённые файлы, выполненные проверки и
  пропущенные проверки с причинами.

Если контракт неоднозначен, окружение недоступно или обязательная проверка не
выполнена, явно укажи ограничение. Не заявляй об успешной проверке, если она
не проводилась.
