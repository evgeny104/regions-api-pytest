# API-тесты Regions API

Контракт поведения API сверяй с `tz.pdf`; тестовые фикстуры смотри в
`tests/func/conftest.py`, а маркеры — в `pyproject.toml`. Не меняй смысл
требований контракта.

## Окружение и запуск проверок

- Работай из корня проекта в `.venv`; команды установки приведены в `README.md`.
- Запускай `pytest`, а не `python -m pytest`, чтобы повторить способ запуска CI.
- Не запускай тесты без просьбы пользователя проверить изменения.
- Функциональные тесты вызывают API. Запускай их только по явной просьбе
  проверить стенд и при настроенном `src/config/url.py` с `BASE_URL`.
- Не устанавливай зависимости глобальным `pip`.

## Порядок работы

1. Прочитай требования `tz.pdf` к сценарию и соседние тесты в `tests/func/`.
2. Сопоставь сценарий с уже существующими проверками и выбери подходящий файл
   по query-параметру или комбинации параметров.
3. Используй pytest и имеющиеся инструменты проекта: фикстуры из
   `tests/func/conftest.py`, Pydantic-схемы, зарегистрированные маркеры и Allure.
   Не добавляй зависимости или новый тестовый фреймворк.
4. Для одного запроса используй indirect-фикстуру `region_response`.
   Для сравнения двух страниц — `region_response_pair`; сохраняй одинаковые
   параметры, кроме номера страницы, если сценарий не проверяет обратное.
   Для последовательных запросов с зависимыми параметрами используй
   `regions_request` напрямую.
5. Сохраняй стиль проекта: параметризуй наборы входных данных через
   `pytest.mark.parametrize` и `pytest.param`, используй читаемые `id`, добавляй
   сценарий в класс с docstring. Первая строка docstring используется для
   группировки теста в Allure.
6. Проверяй статус, валидированное тело ответа и значимые поля по контракту.
   Для негативного сценария проверяй конкретные поля ошибки, когда их задаёт
   контракт.
7. Проверь diff и сообщи изменённые файлы, проверки, которые запускались, и
   проверки, пропущенные с причиной.
8. Используй только зарегистрированные маркеры. Новый маркер сначала добавь в
   `pyproject.toml` и сообщи об этом пользователю.
9. Не ослабляй проверки ради зелёного CI. Подтверждённый дефект помечай
   `pytest.mark.xfail(reason="BUG-XXX: …", strict=True)`.
10. По контракту `total` — число всех регионов и не меняется от фильтров. Не
    вычисляй последнюю страницу по `total` при активном фильтре.

## Интеграция Allure

Функциональные фикстуры уже добавляют в Allure URL, query-параметры и тело
ответа; autouse-фикстура группирует тесты по docstring класса. Используй эти
фикстуры и docstring, чтобы новый тест попал в существующие группы и получил
данные запроса. Не добавляй повторные `allure.attach` или ручные метки без
необходимости. Файлы результатов создаются при запуске pytest с
`--alluredir=allure-results`.

## Подтверждённый дефект API

Если задача включает доказательство нарушения контракта или пользователь просит
оформить такой дефект, используй `.agents/skills/regions-api-bug-reporting/SKILL.md`
для файла в `bug/YYYY-MM-DD/`. Не создавай репорт только на основании гипотезы или
ошибки в тестовом коде.

## Границы роли

Создавай и изменяй API-тесты только в `tests/func/` и не меняй production-код
в рамках роли автора API-тестов. При необходимости
новой фикстуры или изменения общей тестовой инфраструктуры сначала проверь,
что сценарий нельзя выразить существующими средствами, и оставайся в рамках
порученной задачи. API-тесты ходят в сеть и требуют настроенного
`src/config/url.py` с `BASE_URL`.
