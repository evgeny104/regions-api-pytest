# Инструкции проекта: Regions API tests

## Источники и каталоги

- Контракт: `tz-extracted.txt`.
- Чек-лист: `agents-test/checklist/api-checklist.md`.
- Независимые тесты агентов: `agents-test/func/`.
- Результаты агентского прогона: `agents-test/bug/YYYY-MM-DD/`.
- Единый архив отчётов и правила ведения: `agents-test/bug/README.md`.
- Подробные процедуры ролей: `.agents/skills/`; короткие описания агентов: `.codex/agents/`.

`tests/func/` — пользовательская suite и read-only baseline стиля и глубины. Агентские роли её не меняют, не запускают и
не используют как источник дефектов. Координатор может запустить её отдельно, если пользователь явно просит сравнение.

## Последовательность полного агентского цикла

1. **Checklist** разбирает `tz-extracted.txt`, применяет техники тест-дизайна, создаёт атомарные ID и связывает их с
   assertions. Сопоставляет сценарии с `tests/func/`, не превращая неподтверждённые ожидания в контракт.
2. **Author** реализует применимые сценарии в `agents-test/func/` в стиле проекта: клиент и fixtures, Pydantic-валидация
   каждого ответа, параметризация, зарегистрированные маркеры и Allure. Характеризационные проверки помечает отдельно.
3. **Author** запускает и mutation-check только `agents-test/func/`, если запуск поручен пользователем и окружение
   доступно. После каждой мутации восстанавливает assertion и проверяет восстановление.
4. **Reviewer** read-only сверяет каждый сценарий чек-листа с конкретным assertion и возвращает автору устранимые
   пробелы. Следующий этап ждёт исправлений и повторного ревью.
5. **Bug reporter** после прогона и ревью использует только актуальные логи `agents-test/func/`. Создаёт отчёты
   исключительно в `agents-test/bug/`, классифицируя контрактные дефекты, неподтверждённые ожидания теста и
   инфраструктурные ошибки. Не использует `tests/func/` и архивные отчёты как доказательства; архив можно просматривать
   только для выбора уникального ID и предотвращения дубликатов. Создаёт один отчёт на одну установленную причину;
   в отчёте перечисляет все затронутые pytest node ID и результат каждого кейса. Объединяет кейсы только при
   подтверждённой общей причине, а независимые причины описывает раздельно.

## Ограничения

- Не меняй production-код в роли автора тестов.
- Не запускай сетевые тесты без явного поручения пользователя, подготовленного `.venv` и `BASE_URL`.
- Не считай число тестов или assertions доказательством покрытия; веди трассировку по атомарным сценариям.
- Падение characterization-теста само по себе не доказывает дефект API.
- Reviewer не редактирует файлы и не запускает тесты.
- После mutation-check не оставляй временный код, xfail или файлы.

## Завершение

Итог должен содержать изменённые файлы, выполненные проверки и точные результаты, результат независимого ревью,
пропущенные проверки с причиной и ссылки на подтверждённые агентские отчёты. Не заявляй о проверках, которых не было.
