# Инструкции проекта: Regions API tests

## Источники истины

- Контракт публичного API: `tz.pdf`.
- Автор функциональных тестов: `.agents/skills/regions-api-test-authoring/SKILL.md`.
- Независимое ревью: `.agents/skills/regions-api-test-review/SKILL.md`.
- Репорты о подтверждённых дефектах:
  `.agents/skills/regions-api-bug-reporting/SKILL.md`.

Не дублируй в этом файле подробные процедуры из Skills. Здесь определены
маршрутизация задач и взаимодействие ролей.

## Маршрутизация

- Добавление, изменение или исправление функционального теста:
  используй `regions-api-test-authoring`.
- Read-only проверка существующего diff:
  используй `regions-api-test-review`.
- Создание/обновление отчёта о дефекте:
  используй `regions-api-bug-reporting`, только если есть запрос пользователя
  или подтверждённое нарушение контракта.
- Если задача включает изменение тестов и независимую проверку, сначала выполни
  работу автора, затем передай актуальный diff ревьюеру, если оркестратор
  поддерживает делегирование. Не считай ревью выполненным, если оно не запускалось.

## Границы и проверки

- Не изменяй production-код в роли автора API-тестов.
- Reviewer работает read-only и не запускает тесты.
- Не запускай тесты без явной просьбы пользователя.
- Функциональные тесты вызывают API; перед запуском необходимы явная просьба,
  подготовленное окружение и корректный `BASE_URL`.
- Не ослабляй проверки ради прохождения CI.
- Падение теста не является самостоятельным доказательством дефекта API.
- Разделяй подтверждённые факты, гипотезы и недоступные для проверки сведения.

## Завершение задачи

В итоговом сообщении перечисли:
- изменённые файлы;
- выполненные проверки и их результаты;
- пропущенные проверки и причины;
- результат ревью, если оно действительно выполнялось;
- подтверждённые дефекты и связанные отчёты, если они есть.

Не заявляй, что тесты, ревью или другие проверки прошли, если они не проводились.
