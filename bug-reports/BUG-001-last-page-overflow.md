# BUG-001 — Последняя страница пагинации переполнена дубликатами

**Severity:** Major
**Priority:** High
**Component:** `GET /1.0/regions` — pagination
**Env:** `{BASE_URL}` (значение см. `src/config/url.py`)
**Reporter:** evgeny104
**Date:** 2026-10-28

## Описание

На последней странице выборки API возвращает **полную** страницу размером `page_size`, добирая её элементами с предыдущих страниц, вместо того чтобы вернуть **реальный остаток** `total − (last_page − 1) × page_size`.

По ТЗ контракт пагинации стандартный: `page` — порядковый номер страницы, `page_size` — элементов на странице, `total` — общее количество регионов в базе (пример в ТЗ: `total == 22`). Из этого однозначно следует, что страница `N = ceil(total / page_size)` содержит ровно `total − (N − 1) × page_size` элементов.

## Воспроизведение

### Case A — `page_size=5`

**URL:**
```
GET {BASE_URL}?page=5&page_size=5
```

**Expected:** `len(items) == 2` (`22 − 4 × 5 = 2`)
**Actual:** `len(items) == 5`

**Фактический ответ (`items`):**
```json
[
  {"id": 92, "name": "Прага",            "code": "praha",  "country": {"name": "Чехия",    "code": "cz"}},
  {"id": 38, "name": "Санкт-Петербург",  "code": "spb",    "country": {"name": "Россия",   "code": "ru"}},
  {"id": 3,  "name": "Томск",            "code": "tomsk",  "country": {"name": "Россия",   "code": "ru"}},
  {"id": 91, "name": "Усть-Каменогорск", "code": "ustkam", "country": {"name": "Казахстан","code": "kz"}},
  {"id": 17, "name": "Уфа",              "code": "ufa",    "country": {"name": "Россия",   "code": "ru"}}
]
```

Все пять `id` на странице 5 уже присутствовали в выборке страниц 1–4 → **дубликаты**.

### Case B — `page_size=10`

**URL:**
```
GET {BASE_URL}?page=3&page_size=10
```

**Expected:** `len(items) == 2` (`22 − 2 × 10 = 2`)
**Actual:** `len(items) == 3`

**Фактический ответ (`items`):**
```json
[
  {"id": 3,  "name": "Томск",            "code": "tomsk",  "country": {"name": "Россия",    "code": "ru"}},
  {"id": 91, "name": "Усть-Каменогорск", "code": "ustkam", "country": {"name": "Казахстан", "code": "kz"}},
  {"id": 17, "name": "Уфа",              "code": "ufa",    "country": {"name": "Россия",    "code": "ru"}}
]
```

Один лишний элемент сверх реального остатка — такой же тип бага, с меньшей амплитудой.

## Контрольный кейс (без бага)

**URL:**
```
GET {BASE_URL}?page=2&page_size=15
```

**Expected:** `22 − 1 × 15 = 7`
**Actual:** 7 ✅

При `page_size`, близком к `total`, остаток велик и баг не проявляется — отсюда и то, что он не ловился «обычным» тестом на последнюю страницу.

## Инварианты, которые нарушены

1. `len(items_on_last_page) == total − (last_page − 1) × page_size`.
2. **Уникальность `id`** в рамках полной выборки по страницам: регионы `[92, 38, 3, 91, 17]` отдаются дважды.
3. Косвенно — `sum(len(items_pageN)) == total`: сейчас сумма > `total` (24 вместо 22 при `page_size=5`, 23 вместо 22 при `page_size=10`).

## Предполагаемая причина

Похоже на отсутствие нижнего ограничителя для `OFFSET`/`LIMIT` на бэкенде: когда `(page − 1) × page_size + page_size` выходит за реальное число строк, выборка «добивается» до размера страницы, выбирая элементы повторно (вероятно, без корректного `ORDER BY` или с ошибочным циклическим индексом).

## Impact

- Клиенты, которые собирают полный список регионов постранично, получают **дубликаты** и завышенное фактическое число записей.
- Любая дедупликация на клиенте маскирует симптом, но не чинит контракт.

## Регрессионный автотест

Поведение зафиксировано в `tests/func/test_pagination.py::TestRegionsPagination::test_last_page_returns_remainder` — падает на `page_size=5` и `page_size=10`, проходит на `page_size=15`. После фикса сервиса все три кейса должны стать зелёными.
